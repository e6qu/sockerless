| Active branch | `bump-sockerless-cloud-v0.30.3-registry-fixes` |
| Shared code placement | Every component two or more cloud backends carried as copies has one implementation. `backends/core` holds the cloud-neutral pieces: shared-volume configuration (`SharedVolumes`, `ParseSharedVolumes` over a per-cloud `SharedVolumeFormat`, `TranslateSharedVolumeBinds` with a per-backend `HostBindPolicy`), buffered stdin and attach (`StdinPipe`, `BufferedAttachStream`, `CaptureBufferedStdin`, `PublishBufferedAttachResponse`), the bootstrap overlay image (`OverlayImageSpec`, `RenderOverlayDockerfile`, `OverlayContentTag`, `TarOverlayContext`, `OverlayUserEnv`, `HasOverlayRepo`), pod manifests (`PodMemberSpec`, `EncodePodManifest`, `DecodePodManifest`), network-pod materialisation (`UserDefinedNetworkID`, `PendingMembersOfNetwork`, `DeferOrMaterializeNetworkPod`, `HostAliasesForMembers`), pod lifecycle loops (`CloudPodStart`, `CloudPodStop`, `CloudPodKill`, `CloudPodRemove`), `RestartCloudContainer`, the reverse-agent export/pause/unpause helpers, managed-volume shaping (`ListManagedVolumes`, `InspectManagedVolume`, `PruneManagedVolumes`, `InUseVolumeNames`, `ProvisionCache`, the managed-volume tag keys), the DNS-zone discovery skeleton (`DNSZoneDiscovery` over a per-cloud `DNSZoneRecords`), `MapCloudError`, `SplitDockerRef`, `ArchFromPlatform`, the environment readers, `ExecPostHook`, and `RegisterEmbeddedUI`. `agent/envelope` is the exec-envelope wire contract, defined once and imported by the four bootstraps and the four FaaS backends. The `*-common` modules keep what is shared within one cloud family: AWS SDK `LoadConfig`, `ECRPullThroughCache`, `AccessPointToVolume`, and the ECS/Lambda shared-volume formats; Google Cloud `RunVolumes`, `RunVolumeFromBackingSpec`, `GCSSyncPreExec`, `ExtractLogLine`, `URLHost`, and the Cloud DNS record operations; Azure `LogsQuerier`, `LogAnalyticsFetch`, `TagsToMap`, and the Private DNS record operations. Each cloud's error patterns feed `core.MapCloudError`; each storage manager runs on `core.ProvisionCache`. The rule is written down in AGENTS.md: the three `*-common` modules never import each other, and code two of them need is cloud-neutral and lives in core. |
| Buffered attach | One `core.BufferedAttachStream` bounds every buffered attach read on Cloud Run, Cloud Run Functions, Azure Container Apps, and Azure Functions with the bootstrap window plus the run budget, so a stalled invocation releases its reader with EOF (BUG-2948). |
| Azure Log Analytics | One client per backend, chosen at construction from the endpoint coordinate: the Azure SDK client, or over plain HTTP a client that sends the same Microsoft Entra token for the Log Analytics scope itself; the unauthenticated HTTP client and the per-query branch are gone (BUG-2949). |
| Go toolchain | Go 1.26 everywhere: `actions/setup-go` pins `1.26` in every workflow, every harness and smoke image builds from `golang:1.26`, and the workspace and the modules whose dependencies require it declare `go 1.26.0`. The latest `google.golang.org/api` and `golang.org/x/crypto` releases require Go 1.26, and `setup-go` runs with `GOTOOLCHAIN=local`, so a 1.25 runner failed every job at module load until the pin moved. |
| Azure Container Registry authentication | The registry's own token service issues every credential sockerless presents on `/v2/`: a Microsoft Entra token for the `https://containerregistry.azure.net` service audience, exchanged at `POST /oauth2/exchange` for an Azure Container Registry refresh token, traded at `POST /oauth2/token` for an access token scoped to the access the operation needs. Tokens are cached until the `exp` claim of the JWT the registry issued, and re-acquired when a registry answers 401. Covered end to end against the Microsoft Azure simulator by a provisioned registry and a real push, tag, tag-listing and removal round trip. |
| Registry endpoint coordinate | Push, image listing, the multi-architecture index writer and the Artifact Registry tag probe all resolve the registry endpoint through `core.OCIRegistryBaseURL` and keep the Host header naming the registry through `core.SetOCIHost`, so a relocated registry is reachable by every registry operation. A failure to mint a registry credential surfaces instead of being retried anonymously. On Google Cloud the coordinate is read once, `SOCKERLESS_GCP_AR_ENDPOINT` into `Config.ARRegistryEndpoint`, and that value names both the host image references carry (`gcpcommon.OverlayRegistryHost`) and the URL registry HTTP is dialed at (`gcpcommon.RegistryEndpointURL`) for the auth provider, the tag probe (`CheckTagExists`, which reports every non-definite answer as an error), the multi-arch index, and the image resolver (BUG-2946). |
| Docker client credential | `core.RegistryAuthorizationFromDockerAuth` turns the `X-Registry-Auth` a Docker client sends into the `Authorization` value the registry accepts; `BaseServer.ImagePull`, `ImageManager.Pull` for a registry that is not the backend's own, and `ImagePushToEndpoint` present it, an identity token is refused rather than dropped, and a registry that challenges with `Basic` receives the credential directly (BUG-2944). |
| Google harness provisioning | The Cloud Run and Cloud Run Functions harnesses provision Artifact Registry the way Terraform and the operator do against the real service, through `gcp-common/registrytest`: repositories created through the Artifact Registry API and a `docker login -u oauth2accesstoken` with an access token minted from the service-account key, in a Docker configuration directory the simulator process inherits for its own Cloud Build push and Cloud Run pull (BUG-2943; proven against the enforcing v0.30.3 registry in CI). The smoke, GitLab, e2e, and `make stack-*` simulator stacks export `SOCKERLESS_GCP_AR_ENDPOINT` pointing at the simulator, and the CI smoke container runs with `--network host` so the host daemon that runs the workloads reaches the simulator's loopback registry. The Cloud Run and Cloud Run Functions Terraform modules create the `sockerless-overlay` and `gitlab-registry` repositories the backends name. |
| Azure tag listing | The Azure Container Apps and Azure Functions backends request the `pull` action for the Docker Registry HTTP API v2 tag listing behind `docker images`; `metadata_read` belongs to Azure Container Registry's `/acr/v1/` surface (BUG-2953). |
| Simulators | The three cloud simulators, their SDK/CLI/Terraform suites, console SPAs, vendored cloud API specs, and gate scripts live in [sockerless-cloud](https://github.com/e6qu/sockerless-cloud). This repository consumes them as pinned Go modules at the v0.9.2 release: `tests/go.mod` at release commit `723736a8a233e0f3ccb3d6ce0c209a94bfc9afc2`, the harness `ARG SOCKERLESS_CLOUD_VERSION` defaults at the same commit, and `deploy/compose.build.yaml` plus the AWS Lambda live-test checkout at the `v0.9.2` tag. `make install-simulators` builds them into `tests/.build/`. The v0.30.3 release, whose Google Artifact Registry data plane authenticates every `/v2/` request and requires the repository to exist, cannot yet be pinned: its Cloud Run and Cloud Functions hosts pull workload images with no credential from that registry (BUG-2951) and its Azure Container Apps file-share mount fails the shared-volume writer (BUG-2952). When it is, `tests/go.mod` must pin the `ui-auth` support module at the release commit as well — its deleted `v0.1.0` bootstrap tag outranks every pseudo-version and builds the new simulators against the old package. |
| Backends | Seven backends serve the Docker and Podman REST API: Docker passthrough, Amazon ECS, AWS Lambda, Google Cloud Run, Google Cloud Run Functions, Azure Container Apps, and Azure Functions. The six cloud backends are stateless (the cloud is the source of truth, `PendingCreates` the only local state), each implements every `api.Backend` method explicitly, and each assembles networks, multi-container pods, and volumes from its cloud's primitives plus the sockerless agent. Both CI runner topologies (GitHub Actions runner, GitLab docker-executor) are simulator-proven on every container-capable backend; AWS Lambda is the only backend with a green live-cloud cell (BUG-1075). |
| Open bugs | [BUGS.md](BUGS.md) holds 9 open defects: five gated on sockerless-cloud — the AWS simulator's Lambda host resolving cache references locally (2957), — the Google simulator's unauthenticated workload pull from its own enforcing registry (2951), the Azure Container Apps shared-volume writer failing at v0.30.3 (2952), the AWS simulator's cross-run VPC-network reclaim (2950), and the Azure simulator's missing `/v2/_catalog` (2945) — plus the unproven UI CI stall (2925), the moby client migration (2922), the Terraform module hardening findings (2923), and live-cloud validation (1075). |

## Verified Gates

- Every workspace module built and vetted; `golangci-lint` reported no issues on `backends/core`, `gcp-common`, `cloudrun`, and `cloudrun-functions` standalone (`GOWORK=off`), and every changed module and `tests` are tidy standalone.
- The unit suites of `backends/core` (including the private-registry credential test), `gcp-common` (coordinate, auth provider, resolver, probe), `cloudrun`, `cloudrun-functions`, `ecs`, `lambda`, `aca`, and `azure-functions` passed; the integration-tagged files of both Google backends compile.
- The simulator-backed Amazon ECS, AWS Lambda, and Azure Functions integration suites passed on this macOS/Podman host against the pinned v0.9.2 simulators, and earlier against v0.30.3 (the ECS suite on its second run there; the first lost the simulator's VPC network mid-run, BUG-2950). The Cloud Run, Cloud Run Functions, and Azure Container Apps harnesses are Linux-CI-only on this host and run in the PR's CI.
- `backends/azure-common` passed against the pinned simulator, including the Azure Container Registry round trip with the `pull`-scoped tag listing.
- The `tests` module's e2e suite passed locally with every port of a harness reserved together (BUG-2956).
- The Terraform integration harness runs again (BUG-2955): `make tf-int-test-ecs` passes end to end on this host — apply, backend, the act smoke through it, destroy with the sweep — the Lambda environment applies beside the ECS environment it shares its file system and network with, starts its backend and stops at the simulator's local resolution of the function's pull-through-cache image (BUG-2957, so its cell waits outside the CI matrix); the Cloud Run and Cloud Run Functions environments apply, start their backends, build and push the overlay and start the workload in CI, and the Azure environments apply there — all in the `terraform-integration` CI job, one cell per backend, which this host's Podman engine cannot run past the overlay build.

## Invariants

- The user merged pull requests; agents never merged them.
- Sockerless kept at most one open pull request and carried all related work in that branch.
- Pull-request branches were rebased on the freshest `origin/main` before publication.
- No stubs, fakes, mocks, synthetic responses, silent fallbacks, degraded modes, or skipped required tools were accepted.
- Every observed failure was fixed or recorded with evidence in [BUGS.md](BUGS.md).
- Shared behaviour had one implementation, in `backends/core`, `agent/envelope`, or the owning `*-common` module; the per-cloud common modules never imported each other.
