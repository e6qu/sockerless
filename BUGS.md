| 2946 | P3 | Google Artifact Registry's endpoint coordinate is split across two settings that only agree by accident | `NewARAuthProvider` is wired with `config.EndpointURL` (the Google Cloud API endpoint) while `OverlayRegistryHost` reads `SOCKERLESS_GCP_AR_ENDPOINT` (the registry host baked into image references), so `RegistryEndpoint` returns the API endpoint and `IsOverlayCoordinateRegistry` compares against the environment variable | The two coordinates are independent, and the harnesses set both to the same address, so registry HTTP is routed correctly only by construction. Point them at different addresses and image references carry one host while registry requests are dialed at another. The Azure sibling does not have this: `NewACRAuthProvider` defaults to `SOCKERLESS_AZURE_ACR_ENDPOINT` and derives its coordinate host from its own `endpointURL`. Fix shape: give `NewARAuthProvider` the same registry-endpoint coordinate and derive `IsOverlayCoordinateRegistry` from it, rather than from a free-standing environment read. | 2945 | P3 | The Microsoft Azure simulator serves no repository catalog, so `docker images` cannot be exercised against it | `GET /v2/_catalog` answers 404; the simulator's shared OCI registry routes `/v2/<repo>/tags/list` and the manifest and blob endpoints, and Azure Container Registry's own `/acr/v1/_catalog`, but not the Docker Registry HTTP API v2 catalog that `core.OCIListImages` reads first | Real Azure Container Registry serves it, and the ACA and Azure Functions backends read it to answer `docker images`, so the whole listing path is unreachable end to end against the simulator. The endpoint belongs to [sockerless-cloud](https://github.com/e6qu/sockerless-cloud); this entry stays open until it is served there and the pin here advances, at which point the round trip should read through `core.OCIListImages` instead. |

Fix shape, in both harnesses and in the simulator branch only: mint the service-account credential before the pushes rather than after, create each repository with `POST /v1/projects/{p}/locations/{l}/repositories?repositoryId=…` carrying `{"format":"DOCKER"}`, and `docker login <coordinate> -u oauth2accesstoken --password-stdin` with the access token — which is a coordinate-only change, since `gcloud auth configure-docker` does exactly this against the real service. Deferred out of this branch because the enforcing simulator is unreleased, so the change cannot be proven necessary or sufficient against the pinned version, and each harness needs a Docker host and roughly a quarter of an hour per run to prove it does not regress. |
| 2925 | P3 | The user-interface CI job has failed twice for reasons that were budget, not defect | first a twelve-minute stall in `turbo run build` with eleven of twelve packages logged and nothing after, killed by the job timeout; then `ResourceHeaderActions.test.tsx > ECSTasksPage` timing out at vitest's 5s default while the same file reported 34s of transform and 67s of import on the runner. | 2922 | P2 | Two Docker Engine advisories have no released fix, and escaping them is an SDK migration | `govulncheck` reports GO-2026-5668 (a `docker cp` symlink race) and GO-2026-4887 (an authorization-plugin bypass) against `github.com/docker/docker`, reached here from the Docker backend (the three simulators and their shared libraries carry their own copy of this bug in sockerless-cloud). | ~~2941~~ | P3 | The Amazon Web Services simulator harnesses bound the Amazon Route 53 resolver on a fixed port, so they could not start on a host running an mDNS responder | `backends/ecs` and `backends/lambda` launched the simulator without `SIM_DNS_PORT`, leaving it on its 5353 default, and the simulator panics with `bind: address already in use` before serving anything | Any macOS host — and any host running Chrome, whose helper holds UDP 5353 — failed the whole integration suite at startup for a reason that has nothing to do with the code under test. | ~~2940~~ | P3 | A failure to mint a cloud registry credential was swallowed and the operation retried without one | `ImageManager.Pull` logged "cloud auth failed for pull, proceeding without" and continued; `ImageManager.Push` discarded the error with `if token, err := …; err == nil`; `ImageManager.Build` never asked for a credential at all; and `OCIListImages` skipped a repository whose tag listing failed | Each of these turns a credential problem into a different, wrong symptom: a registry that refuses the anonymous retry reports a missing image, and a listing reports the repositories it happened to be able to read as though they were everything the registry holds. All four now surface the failure. `SetOCIAuth` also leaves a request anonymous for an empty token rather than sending a bare `Authorization: Bearer`, which is a credential a registry rejects rather than the absence of one. |
| ~~2939~~ | P3 | The registry endpoint coordinate was honored on some registry paths and ignored on others | `core.OCIPush`, `core.OCIListImages`, `core.AssembleMultiArchManifest` and `gcpcommon.CheckTagExists` each built `https://<registry>` directly, so an operator who relocated the registry — a sovereign cloud, or a harness reaching it at another address — could tag and delete images there but could not push, list, write a multi-architecture index, or probe for an existing tag | The coordinate is now one thing: `core.OCIRegistryBaseURL` resolves it and `core.SetOCIHost` keeps the Host header naming the registry, so a request routed to a relocated address still reaches the registry the reference names — which is what a registry serving several login servers behind one address routes on, and what a registry's token service matches its `service` parameter against. The image-metadata path in `registry.go` honored the coordinate but sent the wrong Host, and now sends the registry's. |
| ~~2938~~ | P1 | Azure Container Registry was handed a raw Microsoft Entra token, which it refuses | `ACRAuthProvider.GetToken` asked Microsoft Entra for `https://<registry>/.default` — an audience Microsoft Entra does not issue, because Azure Container Registry has no per-registry audience — and put the result straight on `/v2/` as a Bearer; `ACRBuildService.AssembleMultiArchManifest` did the same with an Azure Resource Manager token, beside a comment claiming the token exchange was only for tools needing long-lived credentials | Azure documents the opposite: a token is acquired for the container registry *service* audience, `https://containerregistry.azure.net/.default`, exchanged for an Azure Container Registry refresh token at `POST /oauth2/exchange`, and traded with the requested scope for a scoped access token at `POST /oauth2/token` — and only that access token is a Bearer the data plane honours. Both hops now run, behind one token service that caches each token until the `exp` claim of the JWT the registry issued says it expires, re-authenticates when the registry answers 401, and asks for the access the operation needs in the Docker Registry HTTP API v2 scope grammar: `pull` to read a manifest, `pull,push` to write one, `pull,delete` to remove one, `metadata_read` to list a repository's tags, and `registry:catalog:*` for the registry itself. `core.AuthProvider.GetToken` carries the repository and actions to make that possible, which the AWS and Google Cloud providers document as unused because their credentials are registry-wide. Covered end to end against the Microsoft Azure simulator: a registry provisioned through Azure Resource Manager, an image pushed, tagged, listed and removed over `/v2/`, and an assertion that the credential presented is not the Microsoft Entra token it was exchanged for. |
