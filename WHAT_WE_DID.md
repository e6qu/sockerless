## 2026-06-05 — AWS CloudWatch real metrics (BUG-1475, PR pending)

The fidelity audit's strongest lower-priority finding, fixed the way the user asked — **real metrics in the real wire format**, not fabricated and not empty. Removed `computeECSMetric` (which returned invented `CpuUtilized = 0.15×CPU` / `MemoryUtilized = 0.25×mem` a target-tracking autoscaler would compute against); `GetMetricData` now serves the actual datapoints recorded via `PutMetricData` for **every** namespace including `ECS/ContainerInsights` (empty if nothing was pushed — the API-only sim doesn't measure live container CPU). Added real CloudWatch math: `cwAggregate` buckets datapoints into `Period`-second windows over `[StartTime, EndTime)` and `cwApplyStat` reduces each bucket by the requested statistic (Average/Sum/Minimum/Maximum/SampleCount). Writing the first SDK test surfaced two pre-existing protocol bugs the missing test had hidden: the aws-sdk-go-v2 client **gzip-compresses** the `PutMetricData` CBOR body (so the sim 400'd — fixed with `cwReadBody`), and the response must encode timestamps as CBOR **tag-1** epoch, not a bare integer (the SDK rejected it — fixed with a `cwEncMode` that sets `TimeTag: EncTagRequired`). SDK round-trip test asserts each statistic and that ECS metrics serve stored data instead of fabrication. (Added the `cloudwatch` SDK module to `sdk-tests/go.mod`.) Honest scope note: the aws CLI/botocore uses the legacy query protocol for CloudWatch, which the sim doesn't implement for metrics — so the round-trip is via the Go SDK (rpc-v2-cbor); the CLI query-protocol metric surface is flagged as a follow-up.

## 2026-06-05 — AWS IAM policy simulation (issue #427, PR pending)

New `iam_policy_sim.go` implements `SimulateCustomPolicy` + `SimulatePrincipalPolicy` (BUG-1474) — previously `InvalidAction`, so least-privilege IAM couldn't be asserted below the real-AWS tier. Built a real (compact) policy-evaluation engine: parses IAM policy JSON (with the string-or-list `Action`/`Resource` shapes and single-or-array `Statement`), and evaluates an `(action, resource, context)` request with AWS semantics — explicit-deny-wins, `*`/`?` wildcard action matching (case-insensitive) and resource-ARN matching, `NotAction`/`NotResource`, and condition operators (`StringEquals`/`StringNotEquals`/`StringLike`/`StringNotLike`/`StringEqualsIgnoreCase`, `Bool`, `ArnLike`/`ArnEquals`, the `…IfExists` suffix, with `MissingContextValues` reporting) — returning `EvalDecision` of allowed/explicitDeny/implicitDeny. `SimulateCustomPolicy` evaluates the inline `PolicyInputList`; `SimulatePrincipalPolicy` resolves the role's inline (`iamRolePolicies`) and attached-managed (`iamAttachedPolicies` → `iamPolicies`) policies from the store, then reuses the same evaluator. Results are emitted per `(action × resource)`. Coverage: SDK (deny-wins, resource scoping, action wildcards, the `aws:ResourceTag/edd:managed` condition pattern, principal resolution) and CLI (`aws iam simulate-custom-policy` — the consumer's exact least-privilege-assertion shape). No Terraform surface — there is no resource/data-source for policy simulation. Unsupported condition operators conservatively make the gated statement not apply (an Allow can't spuriously grant).

## 2026-06-05 — Fresh fidelity audit: 5 cross-cloud bug fixes (BUG-1468–1472, PR pending)

Ran a fresh fidelity audit (3 parallel agents over the AWS/GCP/Azure simulators hunting fakes/fallbacks/wire-non-conformance), then adversarially verified every candidate against the actual code/SDK before fixing — the agents correctly classified StepFunctions/Batch/CodeBuild/Glue "complete immediately", Lambda container-mode, and deterministic per-resource keys as **intended modeling, not bugs**. Five genuine bugs fixed (all with SDK tests), bundled into one PR at the user's explicit request:

1. **GCP Firestore updateMask (data loss)** — `handleFSPatchDocument`/`handleFSCommit` replaced the whole document, ignoring `updateMask`, so the Firestore SDK's `Update()`/`Set(MergeAll)` (masked writes carrying only changed fields) silently dropped every other field. Added `fsApplyUpdateMask` (no mask → full replace; mask → merge masked paths, preserve the rest).
2. **GCP Secret Manager disabled-version access** — `:access` served DISABLED/DESTROYED versions' payloads. Now returns `FAILED_PRECONDITION` (400) for non-ENABLED versions. Corrected the audit's claim: `latest` = highest version number (NOT "latest enabled") — accessing it when disabled must fail, not skip.
3. **AWS EC2 position-dependent filters** — `Describe{NatGateways,Subnets,RouteTables}` only honored a filter at `Filter.1`; a `vpc-id` filter sent second was ignored → all resources returned. Routed through the general `ec2Filters()` matcher (added a `vpc-id` case to RouteTables too).
4. **Azure App Insights billing PUT (static)** — `currentbillingfeatures` PUT never read the body and returned a static `Cap:100`, so `azurerm_application_insights daily_data_cap_in_gb` drifted perpetually. Now parses, persists per-component, and echoes. (Distinct from the BUG-1467 casing false positive — the PascalCase shape was correct; the bug was static-ignores-input. Tightened the existing test, which had masked it.)
5. **Azure ACR blob digest** — monolithic/chunked blob PUT stored content under the client-supplied digest without verifying; now computes `sha256(data)` and returns `DIGEST_INVALID` (400) on mismatch (matching the manifest path).

Lower-priority audit items left as intended-modeling/cosmetic (AWS ECS fabricated CloudWatch metrics, IMDS-vs-STS accountId, GCS preconditions, ACR checkNameAvailability) — noted for a possible later pass.

## 2026-06-05 — Azure KV version-less key crypto routing (issue #423, PR pending)

`handleKVKey` only routed key crypto (`encrypt`/`decrypt`/`sign`/`verify`/`wrapkey`/`unwrapkey`) for the 4-segment `/keys/{name}/{version}/{verb}` form, so the version-less 3-segment `/keys/{name}/{verb}` — which `azkeys.Encrypt(ctx, name, "", …)` and real Key Vault use to target the current version — fell through to 405 (BUG-1466). Added a `len(segs)==3 && kvIsCryptoVerb(verb)` route that calls `handleKVCryptoKey(..., version="", verb)`; `findVersion("")` already returns `latest()` (the same resolution the version-less GET uses), so no new resolution logic was needed. SDK (`keyvault_versionless_crypto_test.go` — all six crypto ops with version "") and CLI (`az rest` POST `/keys/{name}/encrypt`+`decrypt` round-trip) cover it; there is no Terraform data-plane crypto surface. Internal routing only — no new registered ops, so the surface table and coverage matrix are unchanged.

## 2026-06-05 — AWS ACM DNS-validation issuance + wildcard record name (issues #420/#421, PR pending)

Two coupled ACM fidelity gaps that blocked `aws_acm_certificate_validation` (BUG-1464/1465). **#420**: a DNS-validated `RequestCertificate` (AMAZON_ISSUED) was stored `PENDING_VALIDATION` and nothing ever transitioned it (only `ImportCertificate` set ISSUED), so Terraform polled `DescribeCertificate` to its 45-min timeout. Rather than an unconditional/synthetic transition, `DescribeCertificate` now reconciles via a **Route53 cross-check** (`acmReconcileIssuance` + `acmDNSRecordPresent`): the cert reaches ISSUED only once every domain's `_acm-challenge` CNAME exists in the Route53 sim store — the honest "validation done" signal (a cert with no record stays PENDING, exactly like real ACM). **#421**: the wildcard SAN validation record name was `_acm-challenge.` + domain verbatim (`_acm-challenge.*.devbox.example.com.`), which the provider's consistency check rejects; now built from `strings.TrimPrefix(domain, "*.")` so it's the base domain (the DVO `DomainName` still echoes the wildcard). The header comment was updated to document the new behavior. Coverage: SDK (PENDING→records→ISSUED + de-wildcarded name), CLI (`aws acm` + `aws route53` round-trip), Terraform (new isolated `terraform-tests/acm-validation/` fixture: wildcard-SAN cert + `aws_route53_record` for_each over `domain_validation_options` + `aws_acm_certificate_validation` — the exact consumer flow, which previously hung).

## 2026-06-05 — GCP Cloud KMS service (issue #419, PR pending)

New `simulators/gcp/cloudkms.go` brings GCP to key-management parity with AWS KMS and Azure Key Vault (BUG-1463). Implements the Cloud KMS v1 REST surface: keyRings (create with `keyRingId`, get, list; 404 on missing, 409 on duplicate), cryptoKeys (create with `cryptoKeyId`+`purpose=ENCRYPT_DECRYPT` auto-creating primary version 1, get, list, patch rotation via `updateMask`; 404 when the ring is absent), cryptoKeyVersions (list, get, destroy → `DESTROY_SCHEDULED` with a real `destroyTime`), and `cryptoKeys:encrypt`/`:decrypt`. Crypto is real, not faked — each version gets a random non-exportable AES-256 key and encrypt/decrypt use AES-256-GCM (the ciphertext is framed `version||nonce||sealed` so decrypt selects the version). Responses carry the CRC32C integrity fields `gcloud kms` verifies (`ciphertextCrc32c`, `verifiedPlaintextCrc32c`, `plaintextCrc32c`); incoming bytes accept both standard and URL-safe base64 (gcloud emits URL-safe — the first CLI run failed `illegal base64 data` until that was handled, exactly the issue's note). Coverage: SDK (`cloudkms_test.go` — keyring lifecycle, encrypt/decrypt round-trip with AAD enforcement + malformed-ciphertext rejection, version destroy), CLI (`gcloud kms` encrypt/decrypt file round-trip), Terraform (`fixtures/kms-lifecycle` — `google_kms_key_ring` + `google_kms_crypto_key` apply/destroy). Surface table `specs/SIM_SURFACE_TABLES/gcp-cloudkms.md` + coverage-matrix row added; routes use literal paths so `seed-surface-tables.sh` parses them.

## 2026-06-05 — AWS DynamoDB/ECS fidelity + azf attach-stdin race (PR #418, in-flight)

Closes #416 (DynamoDB GSIs dropped) and #417 (ECS Service family missing), plus ECS/DynamoDB audit follow-ups (BUG-1457–1460). While the AWS-sim work was committed, `test (azure backends)` flaked in CI: `TestAZFGitLabRunnerAttachStdin` hung to a `panic: test timed out after 5m0s` after `Post .../api/function: EOF`. Investigation (not a reorder): the azf `ContainerAttach` overlay path uses a **buffered** exec model (`attach_stream.go` — `Read` blocks until the invoke publishes), faithful to the cloud primitive (ACA/Azure-Functions expose request/response exec, not live bidirectional attach), so the spec-correct client order is write-stdin-before-dispatch. The real defect was in `ContainerStart`'s invoke goroutine: it POSTed the `/bin/sh` exec envelope to the Function App HTTP trigger before the in-container bootstrap bound its port, and the 600s invoke-client timeout stranded the attached reader past go-test's 5-min limit → opaque panic (BUG-1461). Fix: `waitAZFFunctionListening` — a 90s-bounded TCP-readiness probe before the POST, with a clear `function app not ready` fail-fast. Deliberately does **not** use the reverse-agent: `ws://host.docker.internal/...` is unreachable from inside the container under local Podman (confirmed: every reverse-agent path, e.g. `TestAZFContainerExec`, fails locally with the same dial-back error), so the buffered HTTP-invoke path is the one azf path that stays locally validatable — now passes in ~21s. The test was left unchanged; a reorder would have masked the backend bug.

A second flake then surfaced in `tf (aws)` (`TestStackProductionShape`): `Error: listing tags for CloudFront Function (...function/tf-fn/LIVE): ListTagsForResource ... 404 NoSuchResource`. The sim's CloudFront `tagging` handlers (`handleCFListTags`/`TagResource`/`UntagResource`) resolved only **distribution** ARNs (`cfDistributionIDFromARN` → `cfDistributions`); a function ARN missed → 404. The AWS provider tolerates that 404 on some read paths but not others, so it failed intermittently (identical sim code passed runs 26984053264/26985224721, failed 26987472514). Fix (BUG-1462): added `cfStoredFunction.Tags`, a `cfFunctionNameFromARN` resolver, and function-ARN branches to all three handlers, with shared order-preserving `cfMergeTags`/`cfDropTags`. SDK regression added to `TestCloudFrontFunctionLifecycle` (ListTags on a function ARN now 200; tag/untag round-trip).
