## 2026-06-27 - Bigtable gRPC data-plane coverage close-out (BUG-2237) + CloudBuild test-hang fix (BUG-2238) + "No skip-if-absent tests" rule

A new branch `feat/gcp-grpc-dataplane` had been cut with a name suggesting fresh gRPC transport work, but an audit showed PR #656 had already landed the Bigtable Data API v2 gRPC slice on `main` — `bigtable_data.go` (740 lines) implements the full surface (ReadRows with an 18-type RowFilter evaluator, MutateRow/MutateRows/CheckAndMutateRow/ReadModifyWriteRow/SampleRowKeys, in-memory cell store) plus Bigtable admin gRPC, all mounted in `main.go:startGRPCServer` on the port after HTTP. So the branch pivoted from "build it" to "prove it works" — a coverage close-out and second-adaptor audit of the landed code.

The existing `sdk-tests/bigtable_data_test.go` exercised only 2 of the 18 RowFilter types the sim implements (`ColumnFilter`, `LatestNFilter`), 1.5 of the 4 mutation kinds (`Set` + `DeleteRow`), 1 of the 2 ReadModifyWrite rules (`Increment`), never the `MutateRows` batch path or `SampleRowKeys`, and the CLI half of the contract was admin-only (`gcloud bigtable instances/tables create|list`) — the canonical Bigtable data-plane CLI `cbt` was never invoked, so the data plane had no second-adaptor coverage at all. Same shape as the half-fixed surface-table issues: implemented-but-unexercised code silently rots.

The SDK gap was closed by enumerating every implemented surface in the existing test file. `TestBigtable_DataPlane_Filters` runs 18 subtests — one per implemented RowFilter — each seeding deterministic cells and asserting real survival semantics rather than just "no error": which cells a `ValueRangeFilter(["a1","a9")` keeps (the SDK contract is `[start,end)` — end-exclusive — confirmed by reading the SDK source), that `CellsPerRowOffsetFilter(2)` slices the flattened family-asc/qualifier-asc/ts-desc order correctly, that `StripValueFilter` zeroes every value while preserving structure, that `RowSampleFilter(1.0)` keeps every row and `(0.0)` drops every row, that `ConditionFilter`'s predicate selects the true/false branch, that `InterleaveFilters` unions its sub-filters' survivors. Three more tests cover the rest: `TestBigtable_DataPlane_Mutations` (DeleteCellsInColumn/Family/TimestampRange), `TestBigtable_DataPlane_AppendValue` (the second ReadModifyWrite rule, seeding then appending twice and reading back the persisted latest), `TestBigtable_DataPlane_ApplyBulk` (the `MutateRows` batch path, including a partial-failure case proving an unknown-family entry surfaces as a per-entry error while sibling entries stay OK), and `TestBigtable_DataPlane_SampleRowKeys` (150 rows so the sampler's ~100-row cadence produces multiple samples, asserting every sampled key is a real row key). The new tests confirmed the sim was already faithful — the one assertion bug they surfaced (an end-exclusive `ValueRangeFilter`) was in the test draft, not the sim.

The CLI gap was closed by `TestBigtableCLI_DataPlane_cbt`, which provisions the instance via gcloud (admin) then drives `cbt createtable`/`createfamily`/`set`/`lookup`/`read`/`count` over gRPC through `BIGTABLE_EMULATOR_HOST` — the same coordinate the real client uses for the real emulator. `cbt` is built in TestMain via `go install cloud.google.com/go/bigtable/cmd/cbt@v1.13.0` into the test's tmp dir (the last release whose module still ships `cmd/cbt`), so the test runs unconditionally: no skip-if-absent, no PATH dependency. The CLI test harness's `grpcAddr` package var was added so cbt can reach the sim's gRPC server (which the prior harness computed but discarded as a local).

Three boyscout findings rode along. First, the AGENTS.md rule book gained a "No skip-if-absent tests" section: tool-absent `t.Skip` tests are deceptive dead code that reports green while exercising nothing — either install the dependency in `TestMain` (the project already does this elsewhere) or delete the test; the one narrow exception is a `runtime.GOOS`-gated skip for a kernel capability a foreign OS genuinely cannot provide. Second, while running the full gcp sdk-test suite to validate the Bigtable work, the suite hung for 8–10 minutes on `TestCloudBuild_FaithfulBuildPush` whenever the container runtime was unresponsive (Podman-on-macOS wedged in its `unable to upgrade to tcp, received 500` gvproxy state). The test and its setup helpers (`pullImageWithRetry`, `startThrowawayRegistry`) issued `docker pull/run/push` with no per-operation deadline, and the synchronous build POST went through `http.DefaultClient` (also unbounded); a wedged runtime made a single `docker` call hang forever, consuming the entire go-test budget and masking every other test's result. Fixed by bounding every `docker` invocation through a new `dockerCLIWithTimeout(deadline, args…)` helper (180s pull / 60s run/rmi/inspect) and the build POST through a 120s `context.WithTimeout` — a wedged runtime now fails in ~3min with a clear `signal: killed … start throwaway registry` instead of an 8m hang, and a healthy runtime is unchanged. Third, the stale continuity files (`STATUS.md`/`DO_NEXT.md` still described the merged `feat/gcp-ratchet-3` as the active branch) were reconciled to the actual branch state. gcp build/lint(0)/deadcode(0)/dupl(0) + route-validity + doc/spec-consumption + coverage-floor all green.

This branch's CI then surfaced an unrelated AWS-side flake worth fixing at the root (BUG-2225). The cause is that the EC2 `RunInstances` `ClientToken` member carries the Smithy `idempotencyToken` trait, so the aws-sdk-go-v2 auto-fills a UUID for it once, in an initialize step that runs before the retry middleware, and re-sends that same token on every retry. The fix records each successful `RunInstances` reservation under its client token in a new store and replays the original instances (re-fetched for current state) whenever the same token arrives again — faithful EC2 idempotency that removes the duplication at the root rather than papering over the test. ## 2026-06-26 - ELBv2 NLB DescribeLoadBalancers returned the proxy host:port as DNSName (#691, BUG-2223)

A consumer follow-up that corrected a wrong trade-off in the #683 NLB reachability work. To make the new NLB raw-TCP data plane reachable, #683 had `DescribeLoadBalancers` report the proxy's dialable `host:port` as the load balancer's `DNSName`. Because the proxy bound an ephemeral port, that value changed on every run — so terraform-provider-aws planned a perpetual `dns_name` drift — and a `host:port` is not a valid Route53 alias target (an alias needs a hostname plus the ELB's canonical hosted-zone id). The fix makes the reachability faithful instead of hijacking the DNS name: `DescribeLoadBalancers` now always returns the stable AWS-shaped `<name>-<id>.elb.<region>.amazonaws.com` hostname for NLBs and ALBs alike, with `CanonicalHostedZoneId` present so a Route53 alias is valid. Reachability comes the way a real NLB's DNS name resolves to its IPs: the stream proxy now binds the listener's configured port on a stable host — `127.0.0.1`, or, on Linux when another NLB already holds that port, a distinct per-load-balancer `127.0.0.0/8` address leased from a new realexec helper (`ReserveNLBLoopbackIPv4`), which is the real-NLB "each load balancer has its own address" shape and lets many NLBs share a listener port without colliding — and the AWS-shaped DNS name is injected into the workload container's hosts entries (the same `ExtraHosts` mechanism the metadata and Cloud Map services use) so an in-network client resolves the hostname to the proxy and connects on the listener port. That hosts injection is the faithful production consumer of the proxy address, so the whole-program deadcode gate stays satisfied. CreateListener is best-effort on the bind, because real AWS never fails CreateListener for a sim-local socket problem (a privileged port without root, or an off-Linux same-port collision); only the local data plane for that one listener is then unavailable, and it is logged. The change is guarded by a #691 contract test (the DNS name is AWS-shaped, contains no colon, is stable across calls, and carries a canonical hosted-zone id), by the reworked #683 capability test (which resolves the DNS name through the production hosts mapping and then connects on the listener port to prove raw bytes still round-trip), and by a `network` load balancer plus a Route53 alias added to the terraform idempotency stack — a real apply followed by a clean `plan -detailed-exitcode` and destroy.

## 2026-06-26 - ELBv2 TCP target group still returned HealthCheckPath (#688, BUG-2222)

A consumer follow-up to the #685 ELBv2 fix. That earlier change stopped the simulator emitting an HTTP-only `Matcher` for TCP target groups, but `HealthCheckPath` is the same class of HTTP/HTTPS-only health-check attribute and was still leaking: `CreateTargetGroup` defaulted the path to `/` for every protocol and the target-group XML emitted `<HealthCheckPath>` unconditionally, so a TCP target group came back with `HealthCheckPath=/` — which terraform-provider-aws reads into `health_check.path` and then plans as a perpetual drift. The fix generalizes the predicate that #685 introduced (`elbv2MatcherApplies` became `elbv2HTTPHealthCheck`, since it now governs both HTTP-only fields) and adds an `elbv2DefaultedHealthCheckPath` helper: the path is defaulted to `/` only for an HTTP/HTTPS health check, the XML emits the element only for HTTP/HTTPS, and ModifyTargetGroup clears both the matcher and the path when a target group's health check changes to a non-HTTP protocol (and supplies the defaults when it changes to HTTP). A boyscout check confirmed the sibling `ProtocolVersion` attribute is already correctly omitted for TCP, so matcher and path were the complete HTTP-only set. The SDK and CLI fidelity tests now assert the path is absent for a TCP health check and present (`/`) for an HTTP health check on a TCP target group, and the idempotency-fidelity terraform stack's TCP target group gained a TCP `health_check` block so the real-apply-then-`plan -detailed-exitcode` assertion now catches this whole drift class — it passed clean.
