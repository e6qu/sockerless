## 2026-07-08 - bleephub GitHub Actions runner and UI endpoint fidelity (feat/bleephub-faithful-app-runner-flows)

Closed BUG-2363 by removing the remaining Bleephub-only workflow/job execution paths from the external runner harness and workflow UI data paths. `workflow_dispatch` now preserves GitHub's host-mode job shape: a workflow without a `container:` block sends `jobContainer: null` to the runner instead of silently adding an `alpine:latest` job container. The regression builds the runner job message from a dispatched workflow and asserts the host-mode shape directly.

The Docker runner integration harness now creates the real `admin/test` repository through `POST /api/v3/user/repos`, writes each workflow file through `PUT /api/v3/repos/{owner}/{repo}/contents/...`, dispatches through `POST /api/v3/repos/{owner}/{repo}/actions/workflows/{workflow_id}/dispatches`, polls through `GET /actions/runs` / `GET /actions/runs/{run_id}` / `GET /actions/runs/{run_id}/jobs`, and cancels through `POST /actions/runs/{run_id}/cancel`. The resident runner and dispatcher-spawned runner both target `admin/test`, so the same endpoint/credential shape works for Bleephub, GitHub Enterprise Server, and github.com.

The Bleephub web UI moved off the internal workflow store for user-facing workflow pages. The Workflows, Overview, and Workflow Detail pages enumerate repositories through `GET /api/v3/user/repos`, list workflow files through repository-scoped `GET /actions/workflows`, list runs through `GET /actions/runs`, read run detail and jobs through `GET /actions/runs/{run_id}` and `GET /actions/runs/{run_id}/jobs`, and read job logs through `GET /actions/jobs/{job_id}/logs`. The old internal `source` column was removed because it was store metadata, not part of GitHub's workflow object. The Playwright seed path now creates a unique repository, commits a real workflow file, and dispatches it through the same public GitHub Actions endpoints before opening the UI.

Closed BUG-2362 and BUG-2364 by moving GitHub App and OAuth App management off operator-only app-management inventory paths and deleting the legacy internal app-management routes. GitHub Apps list through the signed-in settings surface at `GET /settings/apps`, OAuth Apps list and create through `GET /settings/oauth-apps` and `POST /settings/oauth-apps/new`, installations list through `GET /api/v3/user/installations`, and installation suspend/unsuspend/delete go through authenticated settings routes that call the same store transitions and emit the same installation webhook events as the GitHub App API. The `/internal/apps*`, `/internal/installations`, and `/internal/oauth-apps` app-management routes are gone, and the route-registry guard fails if they return.

Closed BUG-2365 after CI caught a stale GCP simulator module dependency. `simulators/gcp` now pins `cloud.google.com/go/longrunning` v1.2.0, with the related indirect dependency refresh produced by `make upgrade-deps`, and the repository dependency freshness script passes again.

Closed BUG-2366 and BUG-2367 after the full Docker runner integration harness exposed two shell-harness defects. Workflow-dispatch input JSON is now defaulted explicitly only when omitted, so non-empty input objects pass through unchanged. `BLEEPHUB_TEST_FROM=N` now guards each numbered test block independently, so local iteration starts at the requested test number rather than replaying the host-mode tests before the container-mode group.

Closed BUG-2368 after the Amazon EC2 software development kit lifecycle test caught instances staying in `pending` on capable-but-blocked continuous-integration hosts. `RunInstances` now makes the EC2 control-plane state converge to `running` before optional Firecracker host boot work starts, so the public lifecycle no longer waits forever on optional host substrate setup.

Closed BUG-2369 after the required pre-push hook caught fresh Go dependency drift before the branch could push. The affected modules were updated with `make upgrade-deps`: `backends/ecs`, `backends/lambda`, `bleephub`, `simulators/aws/sdk-tests`, and `simulators/azure/sdk-tests`. The refresh brought the AWS EC2/ECS software development kit clients, Bleephub `golang.org/x/crypto` and `golang.org/x/image`, Azure `github.com/coreos/go-oidc/v3`, and related indirect modules to their current published versions.

Closed BUG-2370 after the AWS SDK simulator continuous-integration job showed the broader class behind BUG-2368. The simulator no longer treats local Firecracker VM liveness as AWS EC2 control-plane truth: `DescribeInstances` does not rewrite `running` instances to `stopped` when no VM process is alive, and EBS attach/detach/modify records control-plane attachment metadata while applying real block-device patches only when a live Firecracker VM exists. Capable hosts with blocked or slow Firecracker setup therefore exercise the same EC2 API lifecycle as API-only hosts without inventing a second public state model.

Closed BUG-2371 by moving pull request review-thread listing and resolve/unresolve to GitHub GraphQL. `PullRequest.reviewThreads` exposes store-backed thread state with opaque thread identifiers and review-comment `databaseId` values, `resolveReviewThread` and `unresolveReviewThread` mutate the same stored thread roots, and the pull request UI now reads/resolves threads through `/api/graphql`. The legacy `/internal/repos/{owner}/{repo}/pulls/{number}/review-threads` routes were removed, so user-facing review-thread workflows no longer have a Bleephub-only path.

Closed BUG-2372 by adding a GitHub Container Registry-compatible package publishing data plane. Bleephub now serves the OCI/Docker Registry HTTP API v2 under `/v2/`: registry ping returns the Docker distribution API version header, blob upload sessions accept PATCH/PUT finalization with `sha256:` digest verification, manifest pushes create `container` package versions, and manifest/blob reads serve the stored bytes with `Docker-Content-Digest`. The GitHub REST Packages API remains the management/read surface for package lists, versions, files, delete, and restore. The Packages user interface no longer exposes an "Upload version" modal and no longer calls `/internal/packages`; it manages packages through the GitHub REST package endpoints.

Closed BUG-2373 by tightening package-version storage invariants. A live package can no longer contain multiple active versions with the same name, package file uploads require configured package storage instead of writing below the process working directory, and file payloads/storage paths are validated before the version and file indexes are mutated. Registry publication therefore fails loudly on duplicate references or missing storage instead of creating ambiguous or half-written package state.

Closed BUG-2374 after the required pre-push dependency freshness hook caught stale `golang.org/x/net` pins in `bleephub`, `simulators/aws`, and `simulators/aws/sdk-tests`. The affected modules were refreshed with `make upgrade-deps`, and the repository dependency freshness script passed.

Closed BUG-2375 by removing operator-only download coordinates from public code-scanning responses. CodeQL database archive redirects and CodeQL variant-analysis `query_pack_url` values now point at public non-internal storage routes, while the obsolete `/internal/.../download` and `/internal/.../query-pack` routes are no longer registered. The OpenAPI response observer now records an `internal-url` violation for any successful `/api/v3` JSON response containing `/internal/`, so this class cannot quietly return in another GitHub REST payload.

Closed BUG-2376 after CI caught a transient Go module proxy stream reset in `sim (aws cli compute)` before the simulator tests started. `scripts/ci-go-mod-download.sh` now wraps required simulator `go mod download` setup with three bounded attempts and a final explicit failure, and the simulator SDK/CLI plus AWS SDK prebuild CI paths use it instead of one-shot downloads. The dependency is still required; the wrapper only handles transient transport resets while keeping setup fail-loud after repeated failures.

Closed BUG-2377 after continuous integration caught an opaque process-mode simulator readiness timeout in `sim (aws sdk)`. AWS simulator software development kit, AWS Command Line Interface, and Terraform harnesses now wait up to a bounded 30 seconds for `/health` and report the last observed HTTP status or connection error, so slow startup under hosted-runner load is not mistaken for simulator logic failure. The AWS Command Line Interface harness also controls its dependency more truthfully: it installs a current AWS Command Line Interface when the host binary lacks a recent operation, and command execution fails loudly instead of skipping unsupported operations.

Closed BUG-2378 after the required pre-push dependency freshness hook caught stale Google Cloud Pub/Sub module pins in the Google Cloud simulator and Google Cloud simulator software development kit tests. `simulators/gcp` and `simulators/gcp/sdk-tests` were refreshed with `make upgrade-deps`, bringing Google Cloud Pub/Sub and related indirect support modules to their current published versions.

## 2026-07-08 - bleephub S3 object-store tests use real simulator storage (feat/bleephub-object-store-real-client-tests)

Replaced Bleephub's hand-rolled fake S3 HTTP test server with a real `simulator-aws` process in `SIM_RUNTIME=process`. The S3 filesystem tests now build/start the AWS simulator, create buckets through `aws-sdk-go-v2`, seed objects through `PutObject`, and verify object state through `ListObjectsV2`. File read/write/open-mode semantics stayed covered, and the repo-prefix operations now exercise real object-store pagination by crossing S3's 1000-key default page size. Repo-prefix rename is covered through real S3 copy/delete behavior, matching the path Bleephub uses for S3-backed git storage during repository rename and transfer.

The real object-store test uncovered a simulator fidelity bug: `CopyObject` persisted the destination row under the correct store key but set the row's internal `Key` to the bare object key instead of `bucket/key`. Direct `GetObject` therefore worked while `ListObjectsV2` could not see copied objects. The AWS simulator now stores copied objects with the same canonical key shape as `PutObject`, and both SDK and CLI regressions prove copied objects are list-visible.

Actions byte storage moved in the same direction. `BLEEPHUB_OBJECT_S3_BUCKET` now configures S3-compatible object storage for Actions artifacts, dependency caches, and runner-uploaded log files, with optional endpoint and prefix overrides. Configured object storage fails loudly on startup or write/read errors; delete paths remove object bytes; local development still uses memory or `BLEEPHUB_DATA_DIR` files when no object bucket is configured. Simulator-backed regressions drive the real HTTP handlers and assert artifact/cache/log uploads create the expected S3 objects. Job, run, and run-attempt log downloads now serve only runner-uploaded timeline log files; object-store mode reads those bytes back from S3-compatible storage, and missing uploaded logs return 404 instead of substituting the in-memory live console feed. Stale action-resolution docs/comments were corrected to match the shipped behavior: bleephub-hosted actions serve tarballs from local git storage, and absent action repos/refs fail instead of fetching from github.com.

GraphQL issue sub-issues now use the real issue relationship graph. `Issue.parent`, `Issue.subIssues`, and `Issue.subIssuesSummary` render the same ordered sub-issue links that the REST endpoints create, with summary completion derived from child issue state. Replacing a child issue's parent also persists both affected parents, so a restart cannot resurrect the old parent-child link.

Organization issue-type assignment is real issue state now. Issue rows carry an `IssueTypeID`; REST issue create/PATCH accepts `issue_type_id` and validates it against the repository owner's enabled organization issue-type definitions; GraphQL `Issue.issueType` projects the assigned definition; and the issue sidebar reads the assignment through GraphQL, maps it to the organization issue-type list, and patches the same validated REST field. Assignment rejects disabled and wrong-organization issue types, user-owned repositories do not show a misleading type selector, and reload regressions prove the assignment persists. The sidebar also uses repository owner metadata before making issue-type calls, so user-owned issue detail pages never probe `/orgs/{owner}/issue-types` and do not emit 404 browser console errors under Playwright.

Organization issue-field values are visible through GraphQL now. `Issue.issueFieldValues` projects the same REST-backed custom issue-field rows that `/issue-field-values` creates, using GitHub's issue-field value union, typed field-definition union, select-option objects, enum values, and connection pagination. Text, number, single-select, multi-select, and date values all round-trip from REST writes into GraphQL queries without compatibility mocks or synthetic values.

Projects v2 field values use the same full-store contract through GraphQL. `updateProjectV2ItemFieldValue` resolves and validates the real project, item, and field before writing, accepts exactly one value of the field's actual type, and supports text, number, date, single-select, and iteration values. `Issue.projectItems.fieldValueByName` now renders those persisted values through typed `ProjectV2ItemFieldValue` union members, including iteration metadata from the stored iteration configuration.

GitHub Pages build metadata is git-backed. Manual Pages build requests require an enabled Pages site and a resolvable default-branch commit, then store that actual commit SHA in the build record. Pages builds also use a dedicated persisted ID sequence instead of consuming audit-log IDs, so audit entries and build records no longer affect each other's allocators. Because GitHub's REST build object omits a top-level `id`, reload reconstructs the internal build ID from the persisted build URL while keeping the public response shape intact.

Actions reruns preserve workflow-file identity. Full workflow rerun, failed-job rerun, and job-level rerun resolve cached YAML by the run's originating workflow-file ID/path, preserve that identity through the new attempt, and fail loudly when an old name-only run is ambiguous. Repositories with multiple workflow files sharing the same `name:` no longer rerun whichever same-named file sorts first.

Actions workflow discovery and SDK coverage now exercise the real typed-client path. Workflow-file discovery resolves the repository's recorded default branch when git storage `HEAD` is unset, so repositories initialized through Git Data refs still expose `.github/workflows/*.yml` files to Actions list/get/dispatch. The skipped go-github dispatch test is live coverage now: it creates the workflow file and `main` ref through Git Data, lists the workflow, dispatches it through `CreateWorkflowDispatchEventByFileName`, reads the run by ID, and lists the queued workflow job through the typed SDK.

Actions event ref resolution is fail-loud. Event-triggered and scheduled workflow runs require the triggering ref to resolve to a real git commit; non-empty refs no longer fall back to `HEAD`, missing event refs are rejected before run creation, and scheduled runs reject an unresolved default-branch ref. Reusable workflow file reads also fail when `HEAD` is unresolved. The in-memory workflow git fixtures now create real `main` refs, so tests exercise valid repository state instead of depending on a compatibility fallback.

Bleephub's organization audit-log surface is no longer shape-thin. The owner-gated endpoint lists persisted audit events through the shared GitHub-style paginator, emits Link headers, and searches the actual stored action, actor, org, and detail payload fields through tokenized `phrase` queries. The regression covers exact-action search, cross-field persisted-data search, and page slicing. The README was also brought back in line with implemented reality: implemented audit-log, marketplace `stubbed`, app installation request, webhook config, runner refresh, and organization people-management surfaces are no longer listed as deferred compatibility gaps.

GraphQL issue comments now expose the same persisted pin state as the REST API. `Issue.comments.nodes.isPinned` resolves from the stored `Comment.Pinned` field, and the regression pins a real issue comment through REST before querying it through GraphQL. The stale README claim that legacy numeric-id team routes were deferred was removed because those routes are state-backed and tested.

CI cloud-backend lint is sharded by provider family. The old `lint (cloud-backends)` job ran seven backend modules in one 5-minute shard; on a hosted runner with cold dependency downloads, six modules completed with zero issues before GitHub canceled the job while Azure Functions lint was still running. The lint matrix now runs AWS, Google Cloud, and Azure cloud-backend shards separately, so each provider family has its own timeout budget and runs in parallel.

CI setup no longer streams the Google Cloud CLI archive directly into `tar`. A hosted-runner HTTP/2 stream error truncated that archive in `sim (gcp)` before tests started. The GCP simulator job now downloads the tarball to `$RUNNER_TEMP` with fail-loud retry-all-errors and extracts only the completed file, so transient transport failures retry before the required dependency is used.

Bleephub metadata persistence is SQLite-only, matching the storage split. The unsupported PostgreSQL dialect, `pgx` dependency, CI sidecar, and skip-if-env PostgreSQL test were removed. `BLEEPHUB_DATABASE_URL` now fails loudly with an unsupported-configuration error instead of selecting a second state backend, and the persistence round-trip always exercises SQLite.

The Actions workflow-file reference regression no longer has a rare skip. The test chooses a non-colliding workflow-file path and always asserts that the run's `workflow_id`, `workflow_url`, and `path` reference the originating workflow file rather than the per-run ID.

OAuth authorization and GitHub App setup now use browser-facing flows where GitHub exposes them. The OAuth `?auto=1` shortcut no longer mints authorization codes or selects the seed admin; tests drive login, consent form rendering, CSRF submission, token exchange, and `/user/teams` through the same web-flow path a browser uses. GitHub App creation in the Bleephub user interface and the go-github compatibility tests uses the GitHub App Manifest flow (`POST /settings/apps/new` followed by `POST /api/v3/app-manifests/{code}/conversions`) instead of creating apps through `/internal/apps`. GitHub App installation setup uses the signed-in app-slug browser flow (`POST /apps/{slug}/installations/new`) in server tests, go-github compatibility tests, webhook event coverage, and the gh parity script, so ordinary app-auth fixtures no longer grant arbitrary installation permissions through `/internal/apps/{id}/installations`. OAuth App setup uses the browser settings surface instead of `/internal/oauth-apps`, and the old internal GitHub App/OAuth App management routes are no longer registered.

The user-facing runner and workflow pages no longer advertise Bleephub-internal submission paths. Workflow empty states point users at GitHub Actions workflow files and workflow dispatch; runner empty states point at configuring a GitHub Actions runner against the Bleephub endpoint URL. The follow-up branch closed the remaining runner-control debt by moving the external harnesses and workflow UI data paths to the same GitHub Actions REST endpoints used by github.com, GitHub Enterprise Server, and Bleephub, differing only by endpoint and credentials.

## 2026-07-07 - bleephub PR/release fidelity + continuity cleanup (bleephub-pr-release-fidelity)

Closed the bleephub fidelity backlog left after the large API/UI hardening run (BUG-2313, BUG-2314, BUG-2315).

**PR state is git-backed.** Pull request creation now requires the requested head and base refs to resolve in the repository's git storage, matching real GitHub. The old metadata-only model let tests create PR rows with no git objects behind them, which forced downstream code to invent deterministic pseudo SHAs and default commit counts. That path is gone: REST and GraphQL PR rendering now derive head/base shas, commit nodes/counts, review `commit_id`, status rollups, and merge response shas from real git objects. Merge still materializes the real merge/squash/rebase commit in git storage, and ref resolution now dereferences annotated tags to commits.

## 2026-07-03 - CloudWatch alarm evaluator atomic state transition closes #760 (PR #761)

The `fix/cloudwatch-alarm-evaluator-758` branch closed GitHub issue #760. The related dangling-alarm report #758 was closed by the preceding PR #759.

**Root cause.** The CloudWatch alarm evaluator in `cwEvaluateAlarmsOnce` took a snapshot of every alarm via `cwAlarms.List()`, derived the new state, dispatched actions, and only then wrote the new state back to the alarm record through a separate `cwAlarms.Update`. A concurrent `PutMetricAlarm` request could replace the alarm record between the snapshot and the write, leaving a freshly-created alarm with a stale `StateValue` inherited from the evaluator's in-flight tick. The alarm therefore never transitioned from the stale state and `AlarmActions` were not dispatched.

**Fix.** Moved the entire evaluate / dispatch / persist sequence into a single `cwAlarms.Update` callback so it runs atomically under the alarm store lock. The new state is derived from the live alarm record inside the callback, and the transition is recorded only when the live state differs from the live `StateValue`. Captured the per-alarm closure argument by value so the panic-recovery logger reports the correct alarm name. Added Info-level logging in `cwDispatchAlarmActions` for disabled actions and missing action topics, and in `snsDeliverToSQS` for resource-policy denials and missing target queues.

**Regression test.** `simulators/aws/sdk-tests/cloudwatch_alarm_sns_sqs_process_test.go` gained `TestCloudWatch_AlarmSNSActionToSQS_AfterDeleteAndRecreate`, which starts a fresh `SIM_RUNTIME=process` simulator subprocess, creates an alarm, pumps a breaching datapoint, asserts the SQS subscriber receives the first notification, deletes the alarm, purges the queue, recreates the same alarm name with a fresh metric, pumps another breaching datapoint, and asserts a second notification arrives with `OldStateValue: INSUFFICIENT_DATA`.

## 2026-07-01 - CloudWatch alarm SNS→SQS process-mode fix (#741, PR #742)

A single branch (`fix/aws-cloudwatch-sns-sqs-process-mode-741`) closed GitHub issue #741, which reported that a CloudWatch alarm's SNS action was not delivered to SQS when the AWS simulator ran in `SIM_RUNTIME=process` mode.

**Investigation.** The delivery path itself was sound: the alarm evaluator (`startCWAlarmEvaluator`) transitions the alarm to `ALARM`, fans out through SNS (`snsFanout` → `snsDeliverToSQS`), and enqueues the notification in SQS. The reported empty queue was caused by the external adversarial probe script using `echo "$raw"` to emit the received SQS message; on macOS `/bin/sh` this corrupts escaped JSON sequences, so the first `ReceiveMessage` successfully returned the message but the probe's subsequent parsing and polling could not see it. The probe passes when `printf '%s\n' "$raw"` is used instead.

While investigating, two real racy fallback patterns were found in the CloudWatch simulator storage layer:

- **`simulators/aws/cloudwatch_metrics_query.go`**: `handleCWQueryPutMetricData` read a metric row with `Update`, mutated it, and wrote it back with `Put`. Under concurrent evaluator ticks and `PutMetricData` calls this races and can drop datapoints.
- **`simulators/aws/cloudwatch_alarm_ops.go`**: `cwRecordAlarmHistory` did the same `Update`-then-`Put` dance for alarm-history rows, risking lost history entries.

Both were fixed to use the store's atomic `Upsert` helper.

**Regression test.** `simulators/aws/sdk-tests/cloudwatch_alarm_sns_sqs_process_test.go` starts a fresh simulator subprocess in `SIM_RUNTIME=process`, creates a metric namespace, metric, alarm with an SNS action, SQS queue with a `Principal:"*"` access policy, SNS topic subscription, and asserts the notification is received via `sqs.ReceiveMessage`. The test validates that both the SQS `Body` and the embedded SNS `Message` are valid JSON and that the alarm name round-trips. It uses the same AWS SDK for Go v2 identifiers a real-cloud consumer would use, differing only in the endpoint coordinate.

## 2026-06-26 - ELBv2 NLB DescribeLoadBalancers returned the proxy host:port as DNSName (#691, BUG-2223)
